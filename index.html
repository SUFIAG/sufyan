Selected work

Three systems, and what was actually hard about them

Architecture diagrams all look the same. The interesting part is the constraint you couldn't design around.

Payment processing on the transfer path

Small World Financial Services · London

JavaSpring BootHibernateAWSKubernetes
Problem
A money-transfer network where a payout provider can accept a request, time out before responding, and still have moved the money.
Constraint
No ability to change the provider's API. Retries were mandatory for reliability, and a naive retry is a duplicate payout.
Decision
Idempotency keys generated at the transfer boundary rather than the request boundary, with provider responses reconciled asynchronously against a local state machine instead of trusted synchronously.
Result
Retry-safe payouts under partial provider failure. Alongside it, a rebuilt release pipeline on Docker, Kubernetes, Jenkins and ArgoCD cut deployment time by 40%, and Prometheus/Grafana observability halved time-to-detect on production incidents.

Contractor onboarding, made asynchronous

YeeGoo Technologies · EOR platform

Java 21Spring Boot 3KafkaAWS
Problem
Onboarding a contractor in a new country blocked on third-party identity and compliance checks that could take minutes or days.
Constraint
The flow was synchronous end to end. Users watched a spinner, and every verification provider outage became a platform outage.
Decision
Decomposed onboarding into Kafka-driven stages with an explicit per-contractor state machine, so verification became an event the system waits for rather than a call it blocks on.
Result
Onboarding time down roughly 30%, activation accelerated by about a fifth, and provider outages degraded to delays rather than failures. I led the four engineers who built it, across three time zones.

Watchlist screening compliance teams could live with

BenchMatrix · Risk Nucleus AML platform

JavaSpringSQLScreening APIs
Problem
Sanctions and PEP screening for regulated banks, where the failure mode nobody talks about isn't the missed hit — it's the thousands of false positives that bury the real one.
Constraint
Loosening the matching threshold is a regulatory risk. Screening had to get faster and quieter without getting less sensitive.
Decision
Restructured the query path and the integration with external screening providers, then tightened name-matching and risk-scoring logic so precision improved without moving the recall threshold.
Result
Screening response time down 35% and a materially lighter review queue for client compliance teams — the metric they actually complain about.

AI in production

Where a model earns its place in a financial system

Financial systems are a bad place for magic. Anything non-deterministic has to be auditable, bounded, and reviewable by someone who will be asked to justify it to a regulator.

Document processing that actually ships

A Spring Boot service using AWS Textract for extraction and an LLM for classification and structuring, turning invoices into validated records — around 70% less manual handling in testing. The design point: the model proposes, a confidence threshold decides, and anything below it goes to a person.

Scoring a compliance officer can defend

In Sentinel, anomaly detection sits alongside deterministic rules rather than replacing them. A model can flag; only a rule can block. That split is what keeps the output explainable when someone asks why a transaction was stopped.

Precision over cleverness

The lesson from building AML screening for regulated banks: the win isn't a smarter matching algorithm, it's fewer false positives at unchanged recall. Precision is a compliance-team workload problem before it is a modelling problem.

AI in the loop, not in charge

I use LLM tooling heavily to build faster, and treat everything it produces as a first draft that has to earn its way past tests, review, and a load test before it goes near a payment path.
